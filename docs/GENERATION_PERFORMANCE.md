# 家书生成性能与等待体验说明

最后更新：2026-09-19（Asia/Shanghai）

## 结论

家书生成的主要等待来自真实 Qwen 链路：语音转写、草稿生成和事实复核。2026-09-18 分段实测原配置分别为 10.138、57.798、38.921 秒，总计 106.872 秒。关闭 Qwen 写作/复核默认开启的额外思考后，同素材首次对照为 60.248 秒（约缩短 44%）；仍执行两次写作/审校调用。这是单次对照，不是速度保证。

正常生成提速与异常等待停止分别验收。本轮 `0.2.3` 补齐整次生成、朗读和客户端等待的总时限，使卡住的调用能够结束，并区分“后台已失败”和“客户端暂未读到结果”。本轮没有新增正常生成耗时实测，不能据此宣称再次提速。

`0.2.3` 对应代码 `ff5f8a3` 已通过全量 CI、部署后端并上传微信；后台核实为当前体验版，提交时间为 2026-09-19 02:54:50。当前验证范围、构建哈希及真机待办见 [0.2.3 交付记录](MINIPROGRAM_0_2_3_DELIVERY_2026-09-19.md)。旧 `0.2.2` 记录保留在下文。

## 已实现

### 客户端

- 相机照片在上传前通过 `wx.compressImage` 缩放到最长边 1600、质量 78；截图保留更高质量并缩放到最长边 2048。压缩失败会回退原文件，服务端仍执行 MIME、魔数和大小校验。
- 多张图片的压缩并行执行，减少串行等待和上传体积。
- 生成页显示阶段、已等待秒数和非终态进度：准备素材、理解图片/语音、整理家书、仍需一点时间。
- 等待 90 秒后可回首页；任务编号和幂等键仍保存在本机，后台任务不会被重复提交。
- 达到客户端 180 秒轮询上限时，提示“暂时未读到生成结果，请从最近家书查看”，保留任务编号供再次查询，不再跳进编辑页触发第二次等待。此提示只说明客户端未拿到结果，不能断言后台一定仍在运行。

### API 与模型调用

- 同一批媒体先并行读取，再做总字节数校验，避免逐个读取对象。
- Qwen 草稿与事实复核请求增加按篇幅限制的 `max_tokens`：短笺 720、标准 1050、长信 1500，避免 JSON 已完成后继续生成无用内容。
- 事实复核仍保留第二次多模态调用；不能为了追求表面速度而删除事实来源审校。
- 仅已验证 DashScope Qwen 档案发送 `enable_thinking: false`；其他兼容模型不附带该厂商参数。
- 显式拒绝非正常结束的模型输出；即使截断片段能解析为 JSON 也不接受。
- 私有编辑页展示 ASR 转写并允许更正。更正后重生成直接复用已确认文字，省掉这段音频的再次转写；旧稿在重生成成功前禁止发布和生成持久朗读。
- 图片段落及未确认语音段落标为待核对。识别仍可能错误，须由作者核对，来源 ID 覆盖不代表事实正确。

## 0.2.2：流式语音转写总时限

以下机制已通过自动化验证并随提交 `395aa8f4a4ecd75210f8fc246d78a55a10badef7` 部署：

- 每段流式 ASR 从发出请求到读取完整响应流，共用 `OPENAI_COMPATIBLE_TIMEOUT_MS` 的总时限；当前线上配置为 `60000` 毫秒。供应商陆续返回片段不会重新开始计时。
- 到期即中止请求，返回可重试的 `AI_PROVIDER_TIMEOUT`。已收到但未完成的部分转写全部丢弃，不进入后续写作。
- 该次流式 ASR 禁用 SDK 自动重试，避免重试退避或供应商 `Retry-After` 延长等待；写作、事实复核的现有重试规则不变。
- 客户端把这种终态错误提示为“本次生成已停止”，允许用户手动重试并保留已上传素材；不能继续显示成同一任务仍在后台处理。

`0.2.2` 的此项时限针对**单段流式 ASR**，不是整封家书 60 秒内完成的承诺。当时多段录音、媒体读取、草稿生成与复核仍分别耗时；`0.2.3` 再增加下述整次生成总预算。单段 ASR 截止机制不意味着正常生成再次提速，也没有修复内存任务与家书在服务器重启后丢失的问题。

## 0.2.3：生成、朗读与客户端等待的总时限

以下机制已随 `ff5f8a3` 部署，并进入 `0.2.3` 体验版：

| 操作 | 默认总预算 | 覆盖范围 |
| --- | --- | --- |
| 整次兼容模型家书生成 | 150 秒 | 媒体读取、全部音频转写、草稿、允许的一次空稿补试、事实复核及已有 SDK 重试 |
| 单段流式 ASR | 60 秒 | 等待响应头和读取完整响应流，同时受整次生成剩余预算约束 |
| Qwen / Doubao 朗读 | 120 秒 | 发出请求、接收响应正文和下载最终音频，共用一次预算 |
| 客户端生成结果轮询 | 180 秒 | 查询任务及查询间隔，单次查询回调不返回也不能无限等待 |

- 整次生成由 `OPENAI_COMPATIBLE_GENERATION_TIMEOUT_MS` 控制，默认 `150000`，允许范围 `1000..300000` 毫秒。阶段切换、收到新片段或进入重试都不重新计时；既有单次空稿补试另有 30 秒上限，并服从更早到期的整次预算。
- 草稿和事实复核继续执行，仍保留原有有限 SDK 重试配置；单段流式 ASR 仍指定零次 SDK 自动重试。整次超时会中止底层请求，并以可重试的 `AI_PROVIDER_TIMEOUT` 结束；超时后的迟到素材、转写或草稿不能再触发转写写回、后续模型调用或成功交付。
- 朗读继续使用现有 `QWEN_TTS_TIMEOUT_MS` / `DOUBAO_TTS_TIMEOUT_MS`，默认均为 `120000` 毫秒。Qwen 取得音频下载地址后，不再获得额外的 120 秒；超时以安全错误 `SPEECH_PROVIDER_TIMEOUT` 结束，不使用部分音频。请求和 reader 会取消，清理本身不阻塞返回。
- 客户端网络请求、媒体读取和朗读播放准备增加独立的超时结束路径；失败后释放等待状态，迟到回调不能覆盖新操作。朗读失败时仍可继续查看、编辑或寄出文字家书。
- 必须区分结果未知和服务端终态：客户端回调超时或 180 秒轮询超时，仅表示暂时没有读到最终结果，应保留已有任务编号查询；只有服务端已返回失败，才按“本次生成已停止”处理并让用户主动重试。不能因为查询超时自动重复提交整次生成，也不能保证同一后台任务仍在继续。

本轮界面收尾采用可跳过的 APP 气泡引导，等待和失败提示使用用户能够理解的操作说明；用户界面不展示开发或演示状态。具体引导及最终客户端验收由本轮交付记录说明，不影响上述后台预算。

## 延迟边界

供应商排队、网络、图片大小、录音长度与重试都会影响耗时。此前完整分段数据、事实问题定位及提速部署记录见 [真实多模态测试报告](REAL_MULTIMODAL_TEST_2026-09-18.md)。已部署的历史提速与 `0.2.2` 单段 ASR 停止机制，和本轮 `0.2.3` 整体预算分别核验。本次未新增付费 Qwen 速度对照，不能据此更新正常生成耗时；真机上传、生成、纠错及失败恢复仍需验证。

## 当前推荐配置

`0.2.3` 部署已核实单段 ASR 为 60000、SDK 重试为 1；未显式设置的整次生成与 Qwen 朗读预算分别使用代码默认 150000、120000。当前 Qwen 体验服务的有效配置为：

```env
OPENAI_COMPATIBLE_TIMEOUT_MS=60000
OPENAI_COMPATIBLE_GENERATION_TIMEOUT_MS=150000
OPENAI_COMPATIBLE_MAX_RETRIES=1
QWEN_TTS_TIMEOUT_MS=120000
```

`MAX_RETRIES=1` 允许一次 SDK 瞬时失败重试。2026-09-18 续测开始时，实查服务器为 `TIMEOUT_MS=60000`、`MAX_RETRIES=2`；后续部署时同步为已验证的 `1`，减少网络故障时的重试等待。`0.2.2` 对流式 ASR 单次请求覆盖为零次自动重试，`0.2.3` 保留该规则，写作/复核仍遵循上述配置并受整次 150 秒预算约束。限制异常等待与正常生成提速分别验收。

1. 在 Node `22.23.2`、pnpm `11.19.0` 下运行 `pnpm check` 和 `pnpm build`。
2. 将已验证的 `codex/warm-letter-mvp` 提交部署到香港 API，重启 `warm-letter-api.service`，检查 `/health` 仍为 `demo + WeChat + Qwen profile-match`。
3. 用授权素材完成生成及语音纠错后重生成，记录总耗时与模型错误码；不得把密钥或原始素材写入日志。
4. 在微信开发者工具重新上传小程序，选为体验版，再用任意获授权图片、文字和录音复测：上传、生成、超时离开、首页恢复、编辑确认。

## 后续可选优化

这些项目没有在本轮直接开启，因为会改变安全或供应商边界：

- 用服务端事件推送/长轮询报告真实任务阶段，替代客户端估算进度。
- 为经过授权的媒体做短期对象读取缓存，减少事实复核时的重复读取；缓存必须绑定用户和任务并设置过期清理。
- 评估供应商更快模型或异步批处理，但必须重新完成图片、音频、JSON、来源引用和隐私探针。
- 生产化接入持久化任务队列、共享状态和对象存储；当前单进程内存仓库重启会丢失任务和家书，不能当作生产方案。
